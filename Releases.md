# 0.1.7

### Features & Enhancements
- **"Main power lost" as a dashboard box source (`widgets/dashboard/objects/common.lua`, `docs/developer/dashboard-themes.md`)**:
  - `main_power_lost` is `1` while the main pack is gone and the flight controller is still answering, and `0` otherwise, so a declarative theme can show the state with a plain box and a threshold colour instead of a module of its own. It reads `state.mainPowerLost`, the same answer the *Main power lost* announcement uses.
  - A number and not the boolean, because threshold limits and gauges take numbers and strings only; the same shape as `link_diversity`. It is never `nil`, so before any telemetry it reads `0`, not `--`.
  - It sits at the end of the source list, just before the sensor fall-through, so none of the named sources pays for it; the one comparison is paid by each declared source that falls through to a sensor. `bin/accounting/measure.lua` reports no change on any row.
  - `docs/developer/dashboard-themes.md` lists `esc_load` among the sources again and drops a stray half-sentence below the link section, both left by merging the `esc_load` and link-source changes.
- **The flight record counts voltage sags, so the flight log's `sags` and `sag_min` columns are filled (`tasks/events/telemetry/flight_record.lua`, `tasks/events/ondisarm/tasks/flight_log.lua`, `lib/flight_log.lua`, `docs/reference/flight-statistics.md`, `docs/pages/tools/flight_log.md`)**:
  - `sags` and `sag_min` have been in the log's header since it was written and have always been empty, because the suite had no sag detector. A logged flight now says whether the pack went down under load and how far.
  - **A voltage sag** is a dip to or below the flight controller's own minimum cell voltage — its `vbatmincellvoltage`, one physical fact rather than a second threshold of the suite's — counted once per dip, with 0.05 V a cell of hysteresis so that hovering on the line counts once rather than once a sample. A reading at or below 1 V is the main power gone rather than a sag and is not counted, and the deepest per-cell voltage of a sag is kept beside the count on the record as `minSagCellVoltage`.
  - The cell count is the board's, and telemetry's where the board's is set to auto-detect; where neither answers, nothing is judged and the columns stay empty rather than saying zero. The resolution is the record's 0.5 s sampling interval, which is documented.
  - `sags` is `0` where the pack was watched and nothing happened and empty where it could not be watched at all, so a reader can tell the two apart.
  - The two sag keys deliberately get no box `source`: the dashboard's source table maps a live telemetry reading to that reading's recorded extreme, and a sag count is not one. A theme reads them off `state.flight` by name, which is documented with an example.
- **The flight record keeps a headspeed band per PID profile, so the flight log's `hs1_min` … `hs3_max` columns are filled (`tasks/events/telemetry/flight_record.lua`, `tasks/events/ondisarm/tasks/flight_log.lua`, `lib/flight_log.lua`, `docs/reference/flight-statistics.md`, `docs/pages/tools/flight_log.md`)**:
  - `hs1_min` … `hs3_max` have been in the log's header since it was written and have always been empty, because the record kept one headspeed band for the whole flight. A logged flight now says what the head was held at under each PID profile.
  - **Headspeed per PID profile** is `maxRpmP1`/`minRpmP1` to `maxRpmP3`/`minRpmP3` on the record, taken from the profile the flight controller reports while the reading is sampled. Both ends are taken only while the rotor is under power, through the same gate the lowest headspeed and current of a flight are taken through — the flight controller's governor state in `ACTIVE` or `BYPASS`, held for 2 s, with `FALLBACK` excluded — so the pair is the band the governor held rather than the band the spool-up passed through.
  - Where there is no governor state, the same gate's fallback decides, including its wait of 2 s on both sides of a reading; the PID profile a reading was taken on is held back with the reading, so it is booked to that profile rather than to the one the flight controller reports 2 s later. A reconnect clears the profile with the other readings, so a model without that sensor does not book its samples to the last session's profile.
  - The PID profile is one more sensor the record reads on a sampling pass, and it is offered to the dashboard with the others, so the dashboard does not read it a second time in the same pass.
  - Three profiles, because the log has three column pairs; a flight on profile 4, 5 or 6 goes into the overall headspeed extremes like any other reading and into no per-profile key.
  - The per-profile keys deliberately get no box `source`: the dashboard's source table maps a live telemetry reading to that reading's recorded extreme, and "headspeed on PID profile 1" is not a telemetry reading. A theme reads them off `state.flight` by name, which is documented with an example.
- **A theme can draw "main power lost" (`lib/audio.lua`, `widgets/dashboard/runtime.lua`, `docs/developer/dashboard-themes.md`)**:
  - The suite could already tell that the main pack is gone while the flight controller is still answering on a BEC or a backup battery, but only inside the *Main power lost* announcement and only while that announcement was switched on. A theme that wants to say so on screen had nothing to read.
  - The three tests behind it are now one function (`Audio.mainPowerLost`), which the announcement calls and which the dashboard calls once per telemetry read, publishing the answer as `state.mainPowerLost`. One definition, so a screen and the voice cannot disagree; and the state field is there whether or not the announcement is enabled.
  - Nothing about the announcement changes: the condition, the 10-second repeat and the call when the pack comes back are what they were, and `mainPowerLostActive` stays what it always was -- a record of what has been spoken, which is why it is not the fact being published.
- **Three dashboard box sources for the radio link itself (`lib/link_rates.lua`, `widgets/dashboard/objects/common.lua`, `widgets/dashboard/runtime.lua`, `docs/developer/dashboard-themes.md`)**:
  - `link_packet_rate` names the air rate the link is running at -- `150Hz`, `100Hz Full`, `F1000` -- out of the `RFMD` field of the CRSF link-statistics frame, in the words ExpressLRS itself uses for those rates, for ExpressLRS 3.x and 4.x alike. It is not called `link_rate` because that name is already the flight controller's telemetry link rate in hertz (`session.crsfTelemetryConfig.linkRate`); *ELRS Link* under *Diagnostics* calls this quantity `packetRate` and this follows it.
  - `link_floor` is the receiver sensitivity that rate is specified down to, in dBm, so a theme can turn an RSSI reading into headroom with plain arithmetic instead of a table of its own. The arithmetic stays the theme's; nothing is divided here.
  - `link_diversity` says whether the receiver has a second antenna. It is latched for the flight-controller session and rises only on a reading a second antenna can produce -- a non-zero `2RSS`, or `ANT` naming the second one -- because `ANT` is in every frame and reads a constant 0 on a receiver that has one.
  - ExpressLRS numbers its rates differently in 3.x and 4.x and the frame does not say which, so a theme that declares one of the two rate sources makes the widget send the transmitter module one CRSF device ping; the answer carries its release. Until it has answered, and for a module that is not ExpressLRS 3.x or 4.x, both sources draw `--` rather than a rate the link is not running. Both tables are ExpressLRS's own, cited file by file in `lib/link_rates.lua`; on 3.x the `50Hz` and `250Hz` rates carry no floor, because 3.x gives them one value across two bands with a different sensitivity on each.
  - Nothing is resolved while the link is down: the radio answers every telemetry value with 0 then, and 0 is an air rate.
  - They cost nothing on a theme that names none of them -- no read and no ping -- and one sensor read per telemetry pass on a theme that names one or both of the two rate sources. No shipped theme declares any of the three.
- **The dashboard asks which pack after connecting, and can set that pack's battery profile on the flight controller (`lib/battery_pick.lua`, `widgets/dashboard/battery_pick_menu.lua`, `widgets/dashboard/runtime.lua`, `app/pages/tools/flight_log/`, `docs/pages/tools/flight_log.md`, `docs/dashboard/quick-menu.md`, `docs/developer/dashboard-themes.md`)**:
  - Two new switches on the Flight Log page, both off by default: *Ask which pack after connecting* offers this model's entries from the battery registry once per connection, and *Set the pack's battery profile* lets the pick move the flight controller onto the profile that pack belongs to.
  - The prompt appears **in fullscreen only**, and that is a property of the radio rather than a choice: a widget zone receives no touch and Lua can leave fullscreen but not enter it, so the prompt is what fullscreen shows instead of the quick settings menu until it has been answered or closed, or the model has been armed. Answering it or closing it returns fullscreen to the quick menu, which then carries a *BATTERY* button that brings the picker back while the model is disarmed; no pack is recorded from the picker while it is armed. *NO BATTERY* always has the picker's bottom row, and packs beyond what fits above it are not offered there. The Flight Log page can still record one of them, but a pick there does not switch the flight controller's battery profile.
  - Which profile a pack belongs to is stated in the registry and inferred nowhere else: `profile=1..6` on the entry wins outright, otherwise the entry's `cap=` must match one of the six capacities the flight controller publishes exactly, and where neither answers **nothing is written** — a guessed profile would move the next flight's low-voltage cut. The write is `MSP_SET_BATTERY_PROFILE` plus the EEPROM write, the same pair the quick menu's battery buttons already send, it is skipped when the board reported that profile on connecting and no profile has been written since, and it is refused while the model is armed. Every one of those exits is logged under `rfsuite.battery_pick`, so a pick that changed nothing says which of the six reasons it was instead of looking broken.
  - The pick itself has one implementation now (`lib/battery_pick.lua`): the Flight Log page and the dashboard's picker record it through the same code, into the session the arm edge reads and into the model's own store, so a pack picked in either place cannot end up recorded differently.
  - **A theme can read the prompt and drive it, and draws no part of it.** The prompt's whole state is published read-only as `state.batteryPick`, and `rfsuite.batteryPick` offers select / dismiss / open to anything else on the radio. Documented in `docs/developer/dashboard-themes.md`. The picker is drawn by the widget for every theme, so its way out is always there; a press records a request and the runtime performs it on the next pass, so no card write and no MSP queue turn happens inside an LVGL press callback.
- **The dashboard's fullscreen quick menu builds from an entry list (`widgets/dashboard/fullscreen_menu.lua`, `docs/dashboard/quick-menu.md`) (#207)**:
  - The menu's content is a list rather than drawing code. `M.entries(widget)` returns the rows in the vocabulary `app/manifest.lua` already uses for the tool's own menus -- `id`, `title`, `kind`, `visibleWhen`, `press` -- and `M.build(children, widget, entries)` draws whatever list it is given, falling back to its own when the argument is omitted. A future quick action is a row in that list rather than an edit to shared drawing logic.
  - `kind` is what the builder makes of a row: `action` is a single button, `choice` is a title over a grid of options. The battery-profile grid is a `choice` row rather than a special case inside the builder, and each capacity carries its own label, its own highlight and its own press.
  - The in-flight tuning entry's preview guard is now `visibleWhen = "previewInflightTuning"`, resolved by name against the widget of the pass being drawn. A condition name with no resolver hides its row, which is what an unresolvable condition does in `app/menu_registry.lua`. `enabledWhen`, `lockedWhileArmed` and `confirm` are part of the same vocabulary and no entry sets one, so the first entry that needs one brings its resolver with it.
  - **The battery-profile grid is three buttons wide on a screen at least 400 pixels across when the model carries more than four profiles.** With two columns, six profiles need three rows, and one more action row above the grid than the menu has today would push the third row past the bottom edge of an 800x480 screen, where it would be left out without a word. Three columns keep six profiles to two rows. Four profiles or fewer, and narrower screens, keep the grid they had.
  - **Apart from that grid, nothing on screen changes and nothing a press does changes.** The header, the close button, the two layout profiles, the order of the rows and every colour are what they were. What the menu builds was compared node by node, in every property the builder sets, at both layout sizes and with the preview switch on and off, and each press was compared by the jobs it queues and the state it leaves behind.
  - The quick menu has a documentation page for the first time, and the dashboard documentation index points at it.
- **A dashboard box can show ESC load (`widgets/dashboard/runtime.lua`, `widgets/dashboard/objects/common.lua`, `app/pages/setup/esc_motors/esc_tools/esc_current_limit.lua`, `app/pages/setup/power/preferences/page.lua`, `docs/pages/setup/power/preferences.md`)**:
  - New box source `esc_load`: the current as a percentage of the current limit the speed controller is set to allow. It is a figure a pilot can judge without knowing what the controller is rated for, which a reading in amps is not, and a value above 100 % says the controller is being asked for more than it allows.
  - The limit is not asked for where it can be read. AM32, Scorpion and YGE carry it in their own parameter block, and opening that family's page under *ESC Tools* -- which reads the block anyway -- stores it for that flight controller, in amps, in the same step. Nothing is asked of the flight controller for it, nothing is added to the connect sequence, and a visit that finds the same limit writes nothing.
  - The other seven ESC families report no limit, so *Setup* → *Power* → *Preferences* gains an *ESC Current Limit* row for it. It defaults to *NOT SET*, and with no limit on file an `esc_load` box shows `--` rather than a reading.
  - It costs one division on a pass that has both a limit and a current reading, and a pair of comparisons on a pass that has neither; no telemetry sensor is read for it.

- **The dashboard computes two further flight phases, `armed` and `offline` (`widgets/dashboard/runtime.lua`, `docs/developer/dashboard-themes.md`, `docs/dashboard/user-themes.md`)**:
  - `armed` is the model armed and not yet flying — from the arm until the governor comes up or the throttle passes its threshold. It used to be reported as `preflight`, so the ground screen covered both a model sitting on the bench and a model that is live with the blades turning.
  - `offline` is the post-flight phase once the flight controller has stopped answering. The widget already stopped reading telemetry there so the summary would not decay; the phase now says so, which lets a theme distinguish a model still on the link and armable from one whose numbers can no longer change. What causes it — an unplugged battery, the model out of range, the link gone — the widget cannot tell apart, and the documentation says so rather than naming one of them.
  - **Both are refinements and both are optional for a theme.** A theme declares `armed` and `offline` in its `init.lua` if it wants to draw them; without those keys `armed` resolves to the theme's preflight module and `offline` to its postflight one. Every theme in this repository is unchanged and needs no new file, and the theme selection keeps its three slots — `armed` resolves through the preflight slot, `offline` through the postflight one.
  - **A phase change that resolves to the same module no longer rebuilds the scene.** A rebuild tears the LVGL tree down and builds it again eight boxes per pass, which for a theme that draws the two new phases with its existing modules would have been a rebuild for no visible change — once per arm, and again on every link transition after a flight. Both places that could cause it now go by the module rather than by the phase name: the reload decision in the widget, and the engine's render key, which is built from the new `state.themePhase` instead of `state.flightMode`. Measured on `bin/accounting` against the unchanged tree: the armed scenario builds the scene twice on both, and the worst armed pass — the arm edge — goes from 11956 to 11971 against a target of 12200, with no extra rebuild behind it. The arm edge stays that cheap because nothing on it resolves again: the theme path is memoised by the selection slot, which `armed` shares with `preflight`, and the module every phase resolves to is worked out once when the theme loads, so the phase change compares one lookup.
  - The phase table in `docs/developer/dashboard-themes.md` said arming alone does not leave preflight. That was true and is not any more; the page, that page's own release note in this section and `docs/dashboard/user-themes.md` are corrected in the same change.
- **A dashboard box can show what the speed controller says about itself (`lib/esc_status.lua`, `widgets/dashboard/objects/common.lua`, `widgets/dashboard/runtime.lua`, `docs/reference/esc-status.md`, `docs/developer/dashboard-themes.md`)**:
  - Four new box sources, which are two pairs. In each pair the first is a translated string -- *OK*, *OVERHEAT*, *THROTTLE LOST*, *BEC UNDERVOLTAGE* -- and the second is 1, 2 or 3 so a theme can colour the line, with no value at all where nothing answered. `esc_status`/`esc_status_level` are the worst reading since the flight controller connected; `esc_status_live`/`esc_status_live_level` are what the controller is saying on this pass. Naming either half of a pair declares both halves of it, because they are one reading; the two pairs stand alone.
  - The flight controller already sends the two values this needs, *ESC1 Status* and *ESC1 Model*, and until now nothing read them. The status word has no common layout -- each manufacturer's protocol assigns its own bits -- so the model byte is what makes the word readable at all, and `lib/esc_status.lua` now holds one table per protocol: Kontronik's 24 error and warning flags, Hobbywing V5's eight fault codes, Scorpion's six, Graupner's seven warnings, APD's five, and OpenYGE, whose byte is a motor state and a warning code sharing one byte rather than a flag word.
  - **The five signatures that fill no status word report *NO STATUS*, not *OK*.** Hobbywing V4, BLHeli32, BLHeli_S, AM32 and Castle leave the word at zero, and reading that zero as health would be a claim nothing supports. FlyRotor, XDFly, OMP Hobby and ZTW do fill it but publish no layout, so all that is reported for them is that something is being reported.
  - Severity follows each protocol's own wording: *error* or *protection* is a fault, *warning* or *limit reached* is a warning, and where a protocol calls its whole field warning flags every bit in it is a warning. OpenYGE's three state-dependent codes are read the way its own description makes them -- a warning while the motor runs, a fault with the power cut.
  - **Both readings exist because "now" and "this flight" are different questions, and neither answers the other.** A status line a pilot reads as *what is wrong with my machine* has to follow the controller down as well as up, or it holds an alarm the controller has withdrawn; a value row read as *what this flight has seen* has to keep the worst, or it loses the fault that ended the flight. A controller that cut power for half a second and recovered has said why the flight ended, and a dashboard pass is slower than a fault -- so that reading goes on file until the widget starts a new session with a flight controller. A request to restart the controller is never put on file: the flight controller withdraws it on the next telemetry frame, so it belongs to the live reading alone and a fault already on file outranks it.
  - It costs nothing on a theme that names none of the four: there is no new sensor read, no new state field and nothing in the connect sequence. A theme that does name one pays two sensor reads per telemetry pass and reads the layout again only when one of the two bytes moved -- and one decode answers all four, so a theme showing a live line above a recorded row pays that once.
  - Neither sensor is selected on most flight controllers. *Diagnostics* → *Validate Sensors* lists them under those two labels, and with neither on the radio the box draws `--`.
- **A connection status button in the header (`ui/header.lua`, `ui/home.lua`, `tasks/events/common/runner.lua`, `docs/reference/connection-status.md`)**:
  - The start screen leaves as soon as the flight controller has answered the API version and the unique id, or the wait runs out, and the compile pass has walked the installed tree; the connect sequence then runs on behind the menu with nothing on screen saying so. A flight controller that never answered and one whose configuration is still being read looked the same from the outside, and they are the two a pilot most needs to tell apart. The header now carries a button whose symbol names the state -- no telemetry link, connecting, connected, or something went wrong -- and pressing it opens the detail: which of the two connect phases is running and which step, the reason a handshake failed, or the craft name with the Rotorflight and MSP API versions.
  - It is on every screen the header is on, not only on the main menu. The state matters on a page as much as on the menu: a save refused because the flight controller stopped answering is read on the page it was refused on.
  - **Nothing was moved.** The start screen leaves when it always did, and a tile is enabled when it always was. The button reports the state; it does not gate on it.
  - A connect step that is given up on still counts towards the sequence being finished, so a bare "connected" would have covered a connection missing part of its configuration. `getProgress()` now reports that count beside the total, the button shows the warning symbol, and the notice opens with *Connect steps not completed: n*. It reports the pending task off the same walk, so reporting progress no longer costs two walks of the queue.
  - **A state change rebuilds nothing.** The button's symbol is a text function the firmware resolves on its own refresh pass, and the notice is composed at the press, so nothing is formatted for a state nobody asks about. The connect runner is not looked at again once the sequence is through.
  - One log line per state change, under the `rfsuite.home` tag.
- **A per-flight-controller settings file says which helicopter it belongs to (`lib/model_preferences.lua`, `tasks/events/onconnect/tasks/name.lua`, `docs/reference/configuration-files.md`) (#197)**:
  - The store on the card is named after the board's MCU id and carried nothing a reader could recognise, so a card full of them could only be told apart by hex. The model name the flight controller reports is now written into the file as `craft.name` while a board is connected, which is what #197 asked for.

- **MIN RPM and MIN CURRENT are the floor of the flight, not of the spool-up (`tasks/events/telemetry/flight_record.lua`, `docs/reference/flight-statistics.md`) (fixes #221)**:
  - The two minima were tracked across the whole armed window. A pilot arms first and spools up afterwards, so the first readings inside that window are the lowest ones it will ever carry and they stayed the minimum for the rest of the flight: `MIN RPM` on a postflight tile showed a spool-up or spool-down sample, and `MIN CURRENT` showed the current at arming, which is in practice zero. The maxima beside them were right and are unchanged — nothing about a ramp can raise them.
  - They are now taken only while the rotor is under power, which the flight controller's own governor state decides: `ACTIVE`, where the governor is holding the requested headspeed, and `BYPASS`, where the throttle curve drives the head directly. Spool-up, recovery, throttle idle, throttle hold, autorotation and bailout are ramps or are not driving the head. `FALLBACK` is excluded as well, because the flight controller enters it when the motor rpm signal has failed and a headspeed sampled there is not a headspeed.
  - The gate has to hold for 2 s before a minimum is taken. `ACTIVE` is entered at 99 % of the requested headspeed, so the readings behind the transition are already flight readings and the wait only removes a sample taken on the edge of one.
  - With the governor off or limiting the throttle only, the flight controller never moves the governor state, and a receiver may not be sending that sensor at all. The throttle-or-current half is the rule this suite already applies to the same question when it draws a logged flight; the headspeed term is added here. Its limit is documented: without a governor state nothing says the head has settled, so a slow spool-up on such a model can still reach the minimum.
  - Without a governor state the gate is also held on its way out: a reading is taken only once the gate has held for another 2 s after it. The head can slow before the current falls — the start of a spool-down, a head bogging under load — and while current is still drawn such a reading passes the gate, so the last 2 s of a driven stretch never count. A driven stretch shorter than 4 s therefore leaves no minimum on such a model. The governor state needs no such wait: the flight controller leaves `ACTIVE` and `BYPASS` on the throttle input, before the headspeed falls.

- **The flight controller's UID is read once per connect (`tasks/msp/runtime.lua`, `tasks/events/onconnect/tasks/uid.lua`, `docs/troubleshooting/no-connection.md`) (fixes #410)**:
  - The MSP runtime reads `MSP_UID` itself once the API version is in and its queue is idle, and the `uid` connect task queued a second read of its own whenever the runtime's answer was not yet in the session when the task started. On a link with round trips of a couple of hundred milliseconds that was the usual case: two requests, and two loads of the per-model preferences file within a few hundred milliseconds.
  - The task's read could not deliver anything the runtime's did not. The runtime's `publish()` copies its own UID over `session.mcu_id` after every queue pass, so where the task's reply was the first to land, the UID and the preferences it had written were gone again in the same pass, and the runtime then read the UID a second time anyway.
  - The runtime now owns the read and records when it has an outcome on the current link -- answered, given up after its retries, or not possible at all, because a module it needs is missing, the API version read returned nothing it could parse, or the flight controller's API version is refused. "Given up" means at least once: the runtime still retries after its backoff, and a later answer still reaches the session. The task sends nothing; it waits for that outcome and then marks the preferences resolved exactly as before, with or without a UID. It stays in the connect sequence because it is what puts the UID ahead of the tasks that read `session.mcu_id`.
  - Because the connect sequence now waits on the runtime's read, that read no longer waits for an idle queue: it is queued behind whatever is already there, as the task's own read was. Measured offline with a page client that keeps the queue busy for 100 s from the moment the API version is in: with the idle wait the sequence was held for those 100 s; without it the UID and the preferences are in 1.1 s after link-up and the sequence finishes 6.45 s after link-up, as on master -- where the UID read went out too, but the runtime erased its result, so `session.mcu_id` stayed empty to the end of the run.
  - Measured offline on the dashboard's background tick with the accounting's flight-controller stub and a link of 0.20-0.25 s per round trip: one `MSP_UID` request and one preference load per connect instead of two, and the background tick in which the second reply used to land falls from 7209 to 3219 instructions. Where the flight controller never answers the UID read, the connect sequence finishes 9.05 s after link-up instead of 28.25 s, because the task no longer sits out a read of its own with a 5 s timeout. With a link that answers at once nothing changes: one request and one load, before and after.
  - The runtime's warning for a failed UID read named the command as 2; `MSP_UID` is 160, and the troubleshooting page said the same.
